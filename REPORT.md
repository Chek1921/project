# Отчёт по приёмке сервиса скоринга

Статус: аудит начат. Это рабочий документ: факты проверены чтением кода; сценарии
гонок и исправления ещё должны быть подтверждены изолированными тестами. Время работы
будет указано перед сдачей.

## Что делает проект

Сервис принимает события лидов через FastAPI, сохраняет исходное событие и запись
очереди в SQLite в одной транзакции. Воркеры берут задачи, при возможности обогащают
их профилем партнёра, считают вероятность конверсии и записывают результат в `scores`.
Отчёт агрегирует результаты по аккаунтам владельца. React-панель запрашивает суточный
отчёт и статистику очереди через прокси Vite.

Поток данных: `POST /ingest` → `events` + `queue` → worker → `scores` →
`GET /report` → `web/`.

## Риски

Ниже порядок отражает масштаб последствий, вероятность при четырёх воркерах и
возможность незаметно испортить бизнес-данные. Первые два риска кандидаты на
обязательные бэкенд-исправления: они непосредственно нарушают обещания системы и
искажают отчёт при штатной нагрузке.

1. **Гонка при захвате задачи; обработка не ровно один раз.**
   - Риск: `claim_next` сначала читает `pending`-строку, а затем отдельным `UPDATE`
     отмечает её `processing` без условия `status = 'pending'`. Несколько воркеров
     могут прочитать одну задачу и каждый сохранить score.
   - В проде: в отчётах появляются двойные события и суммы, а партнёрский API получает
     повторные обращения в момент утреннего пика.
   - Обнаружение: текущая `/queue/stats` показывает лишь количества статусов; нет
     метрики повторных score по `event_id`, алерта на неё или конкурентного теста.

2. **Идемпотентность реализована по неверному и незащищённому ключу.**
   - Риск: поиск дубликата фильтрует только `external_id`, хотя договорён ключ
     `(source, external_id)`. В схеме нет `UNIQUE(source, external_id)`, поэтому
     параллельная проверка и вставка допускает и настоящий дубль одной пары.
   - В проде: корректное событие CRM может быть отброшено после одноимённого события
     партнёра; повторная выгрузка при конкуренции может раздуть суммы и очередь.
   - Обнаружение: API возвращает формально успешный `duplicate`; уникальность не
     контролируется базой, а тест проверяет только последовательные запросы одного
     источника.

3. **Дата отчёта и timestamps не соблюдают UTC-контракт.**
   - Риск: API пишет наивный UTC через `utcnow()`, а воркер — локальное время через
     `datetime.now()`. Границы отчёта строятся также в локальном наивном времени.
   - В проде: один результат около полуночи попадёт в разные сутки в зависимости от
     зоны воркера; аналитики получат неповторяемые суточные итоги.
   - Обнаружение: нет смещений (`Z`/`+00:00`), тестов на разные timezone и сверки
     времени хоста с UTC.

4. **Метрика модели не доказывает её качество в проде.**
   - Риск: train-фича `account_conv_rate` рассчитана по всей выборке, включая test;
     `hours_to_status_change` использует дату финальной смены статуса, неизвестную на
     момент скоринга. В инференсе вместо этих данных подставляются глобальная константа
     и нулевой интервал.
   - В проде: фактическая точность может быть существенно ниже ROC-AUC 0.974; лиды
     будут неверно ранжированы без видимой ошибки приложения.
   - Обнаружение: тест проверяет только число в старом `metrics.json`, нет разделения
     данных по времени, проверки доступности признаков или мониторинга качества.

5. **Повторный ручной скоринг удваивает бизнес-агрегаты.**
   - Риск: `/score/{event_id}` всегда добавляет строку в `scores`; отчёт считает все
     строки, а не один актуальный результат на событие.
   - В проде: после ручной проверки сумма и число событий увеличатся, хотя нового
     события не было.
   - Обнаружение: отсутствует уникальность `scores.event_id`, аудит ручных пересчётов
     и тест на неизменность агрегата после повторного score.

6. **Обработка может застрять после падения воркера.**
   - Риск: задача помечается `processing` до работы и никогда не возвращается в
     `pending` по таймауту или при рестарте.
   - В проде: часть лидов навсегда отсутствует в отчёте.
   - Обнаружение: `/queue/stats` не сообщает возраст или число `processing`; нет
     watchdog-а и алерта на старые захваты.

7. **Доступ к отчётам опирается на данные от клиента.**
   - Риск: `X-User-Id` принимается без проверки, `/report` использует переданный
     `user_id`, а `/accounts` отдаёт все аккаунты.
   - В проде: при обходе или неверной настройке прокси пользователь сможет запросить
     чужие отчёты.
   - Обнаружение: нет авторизационных тестов, журналирования отказов или сверки
     запрошенного пользователя с текущим.

8. **Панель скрывает сбои и часть поведения работает неверно.**
   - Риск: ошибки HTTP превращаются в попытку прочитать JSON либо остаются необработанными;
     отсутствуют loading/error-состояния и экспорт. `toISOString()` может выбрать
     предыдущие/следующие сутки относительно локального пользователя.
   - В проде: аналитик увидит пустую или устаревшую таблицу вместо понятного сообщения,
     не сможет выгрузить отчёт и может смотреть не ту дату.
   - Обнаружение: нет фронтенд-тестов состояний, доступности и работы в разных зонах.

## Решения

Пока не реализованы: сначала будут подготовлены воспроизводящие тесты для двух
выбранных бэкенд-проблем, затем маленькие отдельные исправления и коммиты. Не следует
одновременно исправлять все перечисленные риски: это нарушит лимит диффа и не позволит
доказать качество каждой правки.

Панель будет доработана без новой UI-библиотеки: макет уже задаёт CSS-токены и обычная
CSS-реализация укладывается в ограничения задачи. Формат экспорта пока требует
допущения; разумный вариант — клиентский CSV только из уже загруженного отчёта с
понятным именем файла и UTF-8 BOM для корректного открытия в Excel.

## Работа с агентом

Агент использован для первичного чтения требований и трассировки потока данных по
модулям. Для снижения риска широких изменений создана карта `AGENTS.md` с компактным
контекстом. Предварительный вывод агента о гонке очереди нельзя принять на веру: он
будет проверен детерминированным конкурентным/транзакционным тестом до исправления.
